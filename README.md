# 游戏项目研发流程规范（Game Project Playbook）

> 一套给 **10–30 人规模的游戏研发团队**使用的「从创意到发行」流程与交付物标准。
> 目标：让「一个玩法想法」走到「上线发行」的每一步都**有明确交付物、有准入/退出门禁、有风险预案、有复盘闭环**。

## 这份规范解决什么问题

内容型项目（游戏、动画、影视）最常见的三类失控：

1. **返工** —— 「需求没写清楚」没有统一判定标准，评审会开完还是各做各的。
2. **排期失真** —— 里程碑只有日期没有交付物定义，「almost done」可以拖三个月。
3. **风险后知后觉** —— 风险靠人盯，没人系统性记录、跟踪、复盘。

对应地，本规范给三样东西：

| 失控类型 | 本规范的解法 | 在哪 |
|---|---|---|
| 返工 | **DoR（需求就绪定义）**：需求进排期前必须满足什么 | `03-检查清单/DoR-需求就绪定义.md` |
| 排期失真 | **DoD（完成定义）**：五个可二值回答的问题，同行评审确认，不接受自我宣告 | `03-检查清单/DoD-完成定义.md` |
| 风险后知后觉 | **风险登记册 + 里程碑门禁 + 版本复盘 SOP** | `02-模板/` `01-流程规范/` `03-检查清单/` |

## 目录结构

```
01-流程规范/     从创意到发行的阶段划分：每阶段的交付物、准入门禁、退出门禁、常见风险
02-模板/         可直接复制使用的文档模板（立项评估、GDD 大纲、排期表、风险登记册、决策记录）
03-检查清单/     评审与门禁用的勾选清单（DoR、DoD、发布就绪、复盘）
04-案例/         完整跑过一遍的真实案例（本文档的说服力主要来自这里）
05-图表/         全流程图、里程碑甘特图、管线与职责地图
```

## 核心概念（四个词，面试必问）

- **里程碑门禁（Gate）**：每个阶段有「准入」和「退出」两个检查点，退出检查不通过就不能进入下一阶段。
- **DoR / DoD**：需求就绪定义 / 完成定义。DoD 用五个可二值回答的问题取代「差不多做完了」。
- **GDR（Game Decision Record）**：把「为什么砍掉这个玩法」「为什么选这个中间件」这类决策留痕，改自业界成熟的 ADR 实践。
- **复盘闭环**：每次版本结束后固定复盘，**每次只选 1–2 个行动项**，下个版本前必须完成，否则下次复盘第一件事就是追问它。

## 使用方式

1. 先读 `01-流程规范/00-总览.md`，确认阶段划分是否符合你的团队规模（小团队可以合并阶段）。
2. 把 `02-模板/` 里的模板复制到你们实际用的工具（飞书/Notion/Jira/Excel）里。
3. 在第一次需求评审会上就用 `03-检查清单/DoR-需求就绪定义.md` 当场判定，别等会后补。

## 修订记录

| 版本 | 改动 | 触发原因 |
|---|---|---|
| v0.1 | 初稿：双门禁中只有交付物标准；复盘固定 1–2 个行动项 | — |
| v0.2 | 门禁改为**质量锁 + 时间锁**，里程碑必须写明**延期成本/天**与**超期默认动作** | 只卡交付物等于允许无限期打磨，延期的人力开销无人承担 |
