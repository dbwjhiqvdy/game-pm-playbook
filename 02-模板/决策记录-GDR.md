# 模板 · 决策记录 GDR（Game Decision Record）

> 改自业界成熟的 ADR（Architecture Decision Record）实践，本地化为游戏语境。
> **核心价值不是记录结果，而是让半年后的人知道当时为什么没选另一条路。**
> 只写「我们决定用 A」不算决策记录——**必须写清被否决的方案和否决理由**。

---

## 什么情况该写 GDR（不是所有决定都写）

✅ 该写：砍掉/推迟一个功能 · 技术选型（引擎、中间件、数据格式） · 上线节奏（是否软启动） · 美术风格定调 · 数值框架重大调整 · 里程碑范围变更
❌ 不写：日常任务优先级 · 命名与代码风格（这属于规范） · 可随时回滚的小决定

**判断标准**：这个决定如果做反了，半年后会不会有人问「当时为什么这么定」？会，就写。

---

## 模板正文（复制以下内容）

```markdown
# GDR-001 · 决策标题（写成一个问句更好，如「是否砍掉批量替换房间功能」）

- **状态**：提议中 / 已采纳 / 已废弃（被 GDR-00X 取代）
- **日期**：YYYY-MM-DD
- **决策人**：______（最终拍板的人，一个人）
- **参与讨论**：角色列表
- **关联**：里程碑 M2 / 风险 R-001

## 背景与压力

（这一节决定这篇记录有没有价值。写清：现在处于什么阶段、有什么约束、为什么现在必须做决定。
必须包含至少一个**量化约束**：剩余工期、人力、预算、平台窗口期。）

## 候选方案

| 方案 | 成本 | 优点 | 缺点与代价 |
|---|---|---|---|
| A | | | |
| B | | | |
| C（什么都不做） | | | |

## 决策

（选哪个，一句话说清。）

## 决策理由

（为什么是它而不是别的。**这一节要能让反对者信服**，不是复述优点。）

## 被否决方案的关键理由

- 方案 B 被否决，因为：______
- 方案 C 被否决，因为：______

## 后果与影响

- 对排期：______
- 对美术/美术产能：______
- 对发行计划：______
- 遗留风险：______（是否要新增风险登记册条目）

## 复查时点

（什么时候回来看这个决定对不对。例：M3 结束后 / 上线后 30 日数据复盘时。
没有复查时点的决策记录 = 死文档。）
```

---

## 三个常见错误

1. **只写结论不写代价** —— 面试官会问「那你怎么知道这个选择是对的」，你要能说出放弃了什么。
2. **决策人写成一个团队** —— 没有明确拍板人，出问题时无法追溯，也无法复盘。
3. **没有复查时点** —— 决策记录变成事后自我表扬的材料，而不是管理工具。
