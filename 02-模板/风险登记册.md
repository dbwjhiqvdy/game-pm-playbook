# 模板 · 风险登记册

> 用在**每个阶段**，贯穿全程。核心纪律：**没有「触发条件」的风险条目等于没写**。
> 触发条件 = 一个可观测的事实，一旦出现就必须启动应对，而不是继续等。

---

## 字段定义

| 字段 | 说明 |
|---|---|
| ID | R-001 递增 |
| 风险描述 | 写「什么事会导致什么后果」，不写「可能有问题」 |
| 类别 | 技术 / 内容产能 / 依赖外部 / 人力 / 平台与合规 / 玩法验证 |
| 概率 | 高 / 中 / 低 |
| 影响 | 高（影响上线）/ 中（影响里程碑）/ 低（影响体验） |
| **触发条件** | **可观测的事实**。例：「第 3 天结束仍未完成导入导出联调」 |
| 应对措施 | 触发后立刻做什么（提前准备，不是临时想） |
| 责任人 | 一个人名，不是「开发组」 |
| 状态 | 监控中 / 已触发 / 已关闭 |

## 使用规则

1. **每周至少更新一次**，复盘会上第一件事就是过一遍本表。
2. **风险升级必须走决策记录**：一旦某条风险触发并需要砍功能，写 `02-模板/决策记录-GDR.md`。
3. **已关闭的风险不要删除**，标为「已关闭」并写明关闭依据——这是复盘时的素材。
4. **只写你能应对的风险**。写一堆「行业寒冬」这类无法行动的条目，只会让这张表失去信任。

## 常见风险（游戏项目自查清单）

- 技术：引擎版本升级破坏既有功能 / 第三方中间件不再维护 / 性能在低端机型不达标
- 内容产能：美术外包反馈轮次超预期（通常 2–3 轮）/ 关卡返工率高 / 音频需求挤在末期
- 依赖外部：平台认证（Cert）周期（主机通常 2–4 周）/ 本地化排期 / 发行渠道审核
- 人力：关键岗位单人依赖（bus factor = 1）/ 核心成员请假或离职
- 合规：版号与发行资质 / 内购与抽卡相关法规 / 隐私与数据合规
- 玩法验证：核心循环不好玩但发现太晚 / 目标用户与自测人群不匹配
