# Concept: Roguelike 关卡可达性验证 —— 三条路径与代价

- **Slug**: level-editor
- **Created**: 2026-10-04
- **Recommended option**: **Option A（分阶段：先测基线 → 再决定是否做校验扩展）**，且**该推荐是条件性的**——Step 0 的数据可能直接导向"什么都不做"

> **阶段纪律**：以下仅为概念层方案与代价，**不含规格、架构、数据模型、API 设计或任务拆分**（那属于 `/speckit-specify` 之后的工作）。
> 范围前提：按已确认的判断，**语义连通包含钥匙门与条件解锁**——这显著提高了判定复杂度（状态相关可达，而非静态可达）。

## Options

### Option A — 分阶段：先测基线，再在现成编辑器上做校验扩展（推荐）

- **Sketch**：
  - **Step 0**：记录一周真实基线（可达性返工次数、单次返工耗时、策划做一组房间组合的耗时）
  - **Step 1**：若基线支持投入，则**不新写编辑器**，而是在现成编辑器（Tiled 有官方脚本系统；LDtk 有世界布局与邻接数据）之上实现「摆放即校验」的薄层，规则覆盖钥匙门与条件解锁
  - **Step 2**：用 1–2 个版本的数据检验拦截率，再决定是否继续深化
- **Appetite**：medium（Step 0 约 0.5 人日；Step 1 估 **5–8 人日**——高于原先 3 人日的估计，因为含钥匙语义）
- **Trade-offs**：
  - **赢**：复用成熟的摆房间 UI 与导入格式，把投入集中在游戏特有的"设计约束"上（与 Dead Cells 的公开做法一致：通用能力用现成、游戏特有约束自研）
  - **牺牲**：受宿主编辑器扩展能力限制，"摆放即校验"的体验可能不如自研流畅；需跟进上游版本变化
  - **风险**：若 Step 0 数据显示痛感远低于假设，则本方案也不应启动
- **Rabbit holes**：
  - **钥匙/条件解锁的状态空间膨胀**——规则越细，判定成本与维护成本越高
  - **规则随策划改玩法而频繁变更**：维护成本可能长期高于开发成本
  - Tiled 脚本 API / LDtk 扩展的能力边界**尚未实测**，可能不足以支撑即时校验

### Option B — 只做提交后的校验（不追求"摆放时即时反馈"）

- **Sketch**：实现可达性求解（含钥匙语义）并接入 CI，策划沿用现有方式摆房间，提交后自动拦截并定位问题
- **Appetite**：small（估 **3–6 人日**，其中导入器是否已存在是关键变量）
- **Trade-offs**：
  - **赢**：最快、最便宜、风险最低；不依赖任何第三方扩展能力
  - **牺牲**：**未满足 Goals 第一条**（把发现时机前移到创作过程中）——只在提交后报错
  - **风险**：若 CI 反馈周期本身较长，策划体验提升有限，可能不足以改变返工结构
- **Rabbit holes**：CI 结果无人看、或报错信息不具体，导致"多了一个红灯但没人管"

### Option C — 自研完整编辑器

- **Sketch**：独立编辑器，拖拽摆放房间模板 + 即时语义连通校验（含钥匙与条件解锁）+ 直接产出主工程可读的关卡数据
- **Appetite**：large（**≥15 人日**；在"含钥匙语义"的范围下，很可能突破 **25 人日的 kill 线**）
- **Trade-offs**：
  - **赢**：体验最贴合、规则可完全按玩法定制、不依赖第三方
  - **牺牲**：需自行承担 UI、数据格式、导入器、撤销/版本管理，以及**长期维护**——而 research 显示这些正是成本主体
  - **风险**：已知有成熟替代（LDtk 已内建世界邻接数据；Tiled 支持脚本；Unity 商店有 40 美元的图编辑器），差异化难以成立
- **Rabbit holes**：规则持续膨胀；主工程 schema 变更导致编辑器同步改造；**单人维护**风险（团队仅 2 名策划，编辑器开发者往往只有一人）

### Option D — 什么都不做（须作为有效结论保留）

- **Sketch**：维持现状，不为可达性验证单独投入
- **Appetite**：none
- **何时它是正确答案**：若 Step 0 测出的返工成本显著低于假设（例如每版本 < 0.3 人日），则任何投入方案都难以回本
- **说明**：本选项**不是消极默认**，而是需要被明确裁定并记录的结论

## Recommendation

**推荐 Option A，且推荐本身是有条件的**：

1. 它的第一步（Step 0，约 0.5 人日）**几乎零成本**，却能把后续所有结论从 `ASSUMPTION` 升级为事实——这是当前信息缺口下唯一合理的起手式；
2. 它把"通用编辑能力"交给现成工具，把自研压在"游戏特有的设计约束"上，与 research 中 Dead Cells 的公开做法一致，也与 Joel Spolsky 的判据一致（只为核心业务自研）；
3. 在已确认"含钥匙门与条件解锁"的范围下，**Option C 的成本已接近或突破 kill 线**，不应作为首选；
4. **若 Step 0 的数据不支持投入，正确答案是 Option D（不做），而不是从 A 退到 B 硬上。**

> 本推荐的依据强度为 **medium**：目标与代价清晰，但**基线数据与扩展能力边界均未验证**。

## Out of Scope (for the recommended option)

- 替换或改造主工程的关卡数据管线（编辑器与校验必须适配既有管线）
- 美术/场景级编辑能力（地形绘制、光照、特效）
- 程序化生成算法本身
- 服务关卡策划以外的创作角色
- 自研独立编辑器 UI（Option A 明确复用现成编辑器）

## Assumptions to Validate

| # | 待验证假设 | 验证方式 | 若不成立的后果 |
|---|---|---|---|
| V1 | 每版本约 3 次可达性返工、每次约半天 | Step 0 实地记录一周 | 痛感更低 → 转向 Option D |
| V2 | 钥匙门与条件解锁的规则复杂度可控 | 与策划确认规则清单与未来半年预期 | 状态空间膨胀 → Option A 成本逼近 C |
| V3 | Tiled 脚本 / LDtk 扩展足以支撑"摆放即校验" | 半天技术验证（spike） | 退化为 Option B，或需重新评估 C |
| V4 | 主工程导入器已存在或成本很低 | 与主程确认 | 导入器成本可能超过问题本身 |
| V5 | 制作人接受"分步投入、随时可 kill" | 立项评审当场确认 | 无分步空间 → 决策退化为一次性大赌 |
