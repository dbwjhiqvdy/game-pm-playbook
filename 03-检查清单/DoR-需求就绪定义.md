# DoR · 需求就绪定义（Definition of Ready）

> **一句话**：一条需求想进排期，必须先满足下面每一项。不满足就不进排期——不是「先排上再说」。
> **用在哪**：需求评审会当场逐条勾选，勾不满就是**打回**，当场指定「谁、补什么、几天内补完」。

## 为什么需要它

返工的最大来源不是「做错了」，而是「开始做的时候就没说清」。
评审会上大家点头通过、开发做到一半发现「这个交互到底怎么表现」没定义，于是返工。

DoR 的作用是把这种模糊**挡在排期之前**。它不追求需求完美，只要求**可被开发、可被验收**。

## 判定清单（逐条勾选，8 项）

- [ ] **1. 一句话说得清**：能用一句话描述玩家会体验到什么？（说不出，说明还没想清）
- [ ] **2. 核心循环明确**：这条需求接在核心循环的哪一环？玩家做什么 → 得到什么反馈 → 为什么再来一次。
      **工程/工具类需求**（不面向玩家体验，例如内部校验脚本、构建流水线）无循环可言，此项记为**不适用**，不计为缺失——但要改用一条等效判据：「谁在什么场景下用它、解决什么问题」。
- [ ] **3. 验收标准可度量**：写完能拿什么去验？必须是可观察的行为，不是「体验更好」。
      例：「点击图标弹出面板，面板 300ms 内出现，含 3 个页签，切页签时保留滚动位置」。
- [ ] **4. 边界与异常已定义**：断线、背包满、数值为 0、重复点击、中途退出，会发生什么？
      判定门槛是「**至少写出一个具体异常/边界情形的期望行为**」——不必穷举，但一个都没有就是没写。
- [ ] **5. 依赖方已确认**：需要谁配合（美术/音频/后端/本地化/运营）？对方**已经知道并确认了工期**，不是「我等下跟他说」。
      判定要求出现「已确认 / 已答复 / 已同意」这类**确认性表述**；只写「需要后端支持」「等美术出图」「尚未给出排期」不算通过。
      **本需求若没有外部依赖，请明确写出来**（例如「不需要服务端改动」）——不写等于没说。
- [ ] **6. 素材到位或已有排期**：图标、动效、音效、文案是谁出、什么时候出。缺素材会导致「功能做完了但没法上」。
- [ ] **7. 工作量已估算且拆到 ≤3 天**：超过 3 天的任务必须再拆。估不准的，先做 1 天的技术预研再回来估。
- [ ] **8. 风险与砍法已写明**：这条需求的已知风险是什么？如果延期，第一个砍掉的是哪部分？

## 评审会怎么开（20 分钟一场）

| 时间 | 动作 |
|---|---|
| 0–2 分钟 | 需求方用一句话讲需求（**不看文档，直接说**） |
| 2–10 分钟 | 逐条过 DoR 清单，有争议的当场停住讨论 |
| 10–15 分钟 | 估算（可用故事点或人日），超 3 天的当场拆 |
| 15–18 分钟 | 判定：**通过 / 打回**。打回必须写明「补什么、谁补、几天内补」 |
| 18–20 分钟 | 记录决策（写进 `02-模板/决策记录-GDR.md`，含被否决的方案） |

## 不通过怎么办

- **打回不是否决**。打回意味着「材料不齐」，补齐后走快速复评（5 分钟，只看补齐的部分）。
- **同一需求被打回 3 次**，触发一次专项讨论：是这个需求本身不成立，还是流程有问题？如果讨论后仍无法就绪，走立项评估的 **kill** 分支——**把「kill 掉一个需求」也当成成果记录下来**，这比让它烂在排期里强。

## 反模式（这些不算「就绪」）

- ❌「参照竞品做」——竞品没告诉我们你的数值、你的美术产能、你的引擎限制。
- ❌「先做，细节后面再定」——细节后面不会自己定，只会在验收会上变成争吵。
- ❌「UI 简单做一下」——「简单」不可验收。
- ❌ 验收人不到场——验收标准必须由**验收人**确认，不是由需求方单方面写。
